# 冬季道路情報提供インターフェース（線的表示） 課題点レポート

- 作成日: 2026-11-24
- 対象: `main` ブランチ（commit `1c63223`）
- 調査方法: ソースコードの通読、テスト用 `database.db`・`output_24h.json`・`geojson/` の中身の確認、Flask テストクライアントと処理時間の計測

> 本レポートは採否を判断するための材料として、**バグからデザイン・運用・将来機能まで広く**挙げています。
> 優先度は筆者の目安です（**高**: 誤情報・表示不能につながる / **中**: 使い勝手や運用に効く / **低**: 改善提案・将来検討）。

---

## 0. システム概要（把握した内容）

```
[車載センサ/バス] → (リアルタイム登録) → SQLite: pointed_road_data
                                              │
           cron 5分毎: generate_cache.py ─────┤ 直近24hを抽出
                                              ▼
 geojson/(国土数値情報 N13 道路) ──► 最寄り道路へ空間結合(50m以内) ──► 区間ごと集計
                                              │
                                              ▼
                                    output_24h.json (約25MB)
                                              │
  Flask app.py ── /api/roads/recent ◄─────────┘ (キャッシュをそのまま返す)
              └── /api/roads/search ── 任意期間をその場で DB 検索・集計
                                              │
                Apache (/WinterRoad-Overview-LineStyle) リバースプロキシ
                                              │
  ブラウザ: Leaflet + 地理院淡色地図 + noUiSlider
    - WIPS / 路面状態 の色分け表示、凡例兼フィルタ
    - 時間スライダー（クライアント側で最終観測時刻により絞り込み）
    - 区間クリックで詳細・路面画像表示、地図→パネルへ矢印線
    - 5分自動更新、カレンダーによる過去データ検索
```

計測値（テストデータ・本機）:

| 項目 | 値 |
|---|---|
| 対象道路セグメント数 | 47,410 本（すべて LineString） |
| 直近24h でデータが紐付く区間 | 約 1,000 本（**全体の約2%**） |
| `/api/roads/recent` のレスポンス | 約 **24.8MB**（非圧縮） |
| `pointed_road_data` 件数 | 約 431 万件（2026-01〜2026-11） |
| 道路 GeoJSON 読み込み | 約 5 秒（起動時・cron 毎回） |
| 過去検索: 1日 / 1週間 / 1か月 | 2.3 秒 / 3.9 秒 / 10.6 秒（いずれもレスポンス約25MB） |
| `get_at` のインデックス | **なし**（フルスキャン） |

## 1. 機能バグ・不具合（誤表示につながるもの）

### 1-1. 【高】過去データ検索の結果がほぼ全区間「データなし」で表示される
- `fetchHistoryRoadData()` は描画時に `refreshLayerStyles()` を呼びますが、これは**時間スライダーの範囲（直近24h）**で `last_updated` を絞り込みます（`static/js/app_main.js:106`, `styles_and_filter.js:31-35`）。
- 既にレイヤーが存在する場合、`addData` 時のスタイル関数もスライダー範囲を使います（`app_main.js:40-44` で初回生成されたもの）。
- 結果、カレンダーで指定した過去期間のデータは「範囲外」と判定され灰色の細線になります。**過去検索機能が事実上機能していない**可能性が高いです。
- 対策案: 過去検索中はスライダーによる絞り込みを無効にする、もしくはスライダーの範囲自体を検索期間に切り替える。

### 1-2. 【高】WIPS に `-Inf` が含まれると画面全体が読み込めなくなる
- テストDBに `WIPS = -Inf` が 20 件存在します（例: 2026-01-24 10:01:07）。
- 集計の `mean` が `-inf` になり、`to_json()` → `jsonify` / `json.dump` は `-Infinity` を出力します。これは**JSON として不正**で、ブラウザの `res.json()` が失敗し「更新エラー」になります。
- 1点の異常値で全道路が表示されなくなるため影響が大きいです。
- 対策案: DB取得時に `NaN/±Inf` や物理的にあり得ない値を除外、`json.dumps(..., allow_nan=False)` で検出、異常値ログ出力。

### 1-3. 【高】凡例のチェックボックス（フィルタ）がほぼ効かない
- `getFeatureStyle()` で非表示になるのは「時間範囲外 かつ `wips_none` がオフ」の場合だけです（`styles_and_filter.js:40-45`）。
- 「危険のみ表示」「凍結のみ表示」などの操作をしても、該当カテゴリの線は消えません。
- 路面モードの「データなし」(`surface_none`) もフィルタとして機能していません。

### 1-4. 【高】時間スライダーの範囲がページ読み込み時点で固定される
- スライダーの `max` はページ読み込み時刻で固定（`slider.js:2-8`）。5分自動更新でデータが新しくなっても、**読み込み時刻より後の観測はスライダー範囲外として灰色表示**されます。
- 開きっぱなしの監視画面（運用上もっとも想定される使い方）ほど、最新情報が見えなくなります。
- 対策案: 自動更新ごとにスライダーの範囲を更新し、右端に張り付いている場合は終端も追従させる。

### 1-5. 【高】過去検索後に「現在時刻モード」へ戻れない
- 過去検索で `customSearchMode = true` になり、これを戻すのはスライダー操作のみです（`slider.js:47-50`）。
- 「現在時刻モード」のチェックを入れ直しても自動更新は再開されず、即時の再取得も行われません。
- 逆にスライダーを触ると `customSearchMode=false` になる一方で、表示データは過去検索結果のままです（状態の不整合）。
- 対策案: 「現在/過去」のモードを明示的な切替 UI にし、切替時に必ずデータを取り直す。

### 1-6. 【高】路線名が「3」「5」などの数字で表示される
- `format_route_name()` は `N13_006` を路線名として扱っていますが、実データでは `N13_006` は 1〜5 のコード値で、路線名ではありません（`services/road_loader.py:12`）。
- `output_24h.json` の `display_route_name` は全件が `"1"`〜`"5"` の5種類のみです。
- N13 データには路線名属性がないため、別データ（国土数値情報 N06 等や OSM）との突合、または「区間ID＋道路種別名」表示への変更が必要です。

### 1-7. 【中】集計の「最新」が最新とは限らない
- `road_surface` と `image_path` は `x.iloc[-1]`（グループ内の最後の行）ですが、事前に `get_at` で並べ替えていません（`services/aggregator.py:26-31`）。
- SQL にも `ORDER BY` がないため、**「最終更新」の時刻と、表示している路面状態・画像が別の観測**になり得ます。
- 対策案: `ORDER BY get_at` を付ける、または `idxmax` で最新行を取る。

### 1-8. 【中】WIPS を「期間内の平均」で表示している
- 24時間の平均値を表示しているため、一時的な危険（凍結した時間帯）が平均で薄まります。安全情報としては「最新値」「最小値（最悪値）」の方が意味がある可能性があります。
- 一方で路面状態は「最後の1件」なので、**WIPS は平均・路面は最新という不一致**も生じています。
- 対策案: 指標の定義（最新/最悪/平均）を決め、詳細パネルには観測件数・最小・最大も表示する。

### 1-9. 【中】時間スライダーの意味がユーザーの直感と異なる
- スライダーは「最終観測時刻が範囲内の区間を表示」するだけで、**表示される値は常に24時間全体の集計値**です。
- 例: 0〜5時を選んでも、10時に再観測された区間は消え、残った区間の値も24h平均のままです。
- 対策案: 観測点単位の時刻情報をクライアントに渡して範囲内で再集計する、またはサーバー側で時間帯別に集計した結果を用意する。

### 1-10. 【中】`get_feature_style` の「データあり」判定が路面モードでも WIPS 基準
- 路面モードでも `props.wips` の有無で太線/細線を決めています（`styles_and_filter.js:37`）。路面状態はあるが WIPS が欠損、のような場合に表示が崩れます。

### 1-11. 【中】画像パスの生成が文字位置の決め打ち
- `p.image_path.slice(26, -4)` や `slice(6, 12)` で固定位置を切り出しています（`app_main.js:139`）。
- カメラ番号が2桁になる、ファイル名規則が少し変わるだけで画像が出なくなります。サーバー側で正規表現により URL を組み立てて返す方が安全です。

### 1-12. 【中】入力値の検証がない
- `/api/roads/search` はパラメータ無し、開始＞終了の逆転、不正な形式でも 200 を返し、全区間データなし（約22MB）を返します。
- モーダル側でも開始＞終了のチェックがありません。ユーザーには「該当なし」なのか「入力ミス」なのか区別できません。

### 1-13. 【低】`get_at` を文字列で比較している
- クライアントでの時間判定は `"YYYY-MM-DD HH:MM:SS"` 文字列の大小比較です。DB側の形式が少しでも変わる（`T` 区切り、ミリ秒、タイムゾーン付き）と破綻します。

### 1-14. 【低】タイムゾーンの前提が暗黙
- サーバーは `datetime.now()`（サーバーのローカル時刻）、クライアントはブラウザのローカル時刻、DBの `get_at` のタイムゾーンは不明です。海外や UTC 設定のサーバー・端末で時間がずれます。

## 2. デザイン・UI

### 2-1. 【高】画面の大半が灰色の「データなし」線で埋まる
- 47,410 区間のうちデータありは約2%。灰色線が地図全体を覆い、**本当に見たい色付き区間が埋もれます**。
- 対策案: データなしは既定で非表示（または非常に薄く）、ズームレベルに応じて表示、観測ルート（バス路線）だけを背景表示する。

### 2-2. 【高】配色が危険度の序列を表していない（路面モード）
- 凍結=紫、スラッシュ=茶、新雪=水色、湿潤=青、半湿潤=シアン、乾燥=緑と、**色相がバラバラで危険度の順序が読み取れません**。
- 「湿潤」の青 `#2c7bb6` は WIPS モードの「良好」と同じ色で、モードを切り替えると同じ色が別の意味になります。
- 半湿潤 `#00a896`・新雪 `#00bfff`・湿潤 `#2c7bb6` は似た寒色で判別しづらいです。
- 「その他」(`#ff7f0e`) は凡例に載っていません。
- 対策案: 乾燥→湿潤→シャーベット→積雪→凍結 の順に段階的な配色（例: 緑→黄→橙→赤→濃紫）を割り当てる。

### 2-3. 【中】色覚多様性への配慮
- WIPS の赤/橙/青は比較的良いものの、路面モードは緑と赤系・紫と青系の区別に依存しています。
- 色だけでなく、線種（破線）、太さ、アイコン、ツールチップの文字情報を併用すると、カラーユニバーサルデザインに近づきます。

### 2-4. 【中】選択中の区間が地図上で強調されない
- 区間をクリックしても線自体の見た目は変わらず、矢印線だけが手がかりです。選択区間を太くする・縁取りを付ける等が必要です。
- 区間は数十〜数百m単位で細かいため、**線が細い/短い区間はクリックしづらい**です（特に灰色の 3px 線）。

### 2-5. 【中】矢印線（コネクタ）の挙動
- 矢印の先はパネルの縦中央固定で、パネルがスクロールされていたり詳細部分が画面外にあると、何も無い場所を指します。
- 選択区間が地図外にスクロールしても矢印が画面外から伸び続けます。
- 上部バーやパネルの上を横切るため、他の情報を隠すことがあります。

### 2-6. 【中】画面タイトル・用語の不統一
- `<title>` は「国道状態モニタリングシステム」、パネルは「道路モニタリング」、README は「冬季道路情報提供インターフェース」。実際は高速・国道・主要地方道を対象としており「国道」は不正確です。
- 「WIPS」が何の指標か、数値の意味（何点満点か、なぜ 7.5/8.0 が閾値か）が画面上に説明されていません。一般利用者には理解できません。
- 凡例が英語＋日本語混在（`Dry (乾燥)` など）。対象ユーザーに合わせて統一を。

### 2-7. 【中】時間スライダーの目盛りに日付がない
- 目盛りは `HH:MM` のみで、日付をまたぐ24h範囲では「どの日の 03:00 か」が分かりません。
- スライダー初期値が「直近6時間」なのに、見出しは「直近24時間の時間範囲指定」となっており、初見では表示範囲が分かりにくいです。

### 2-8. 【中】「最終更新」がデータの鮮度を表していない
- ステータスの「最終更新」は**ブラウザが取得した時刻**で、キャッシュの生成時刻や最新観測時刻ではありません。cron が止まっていても「最終更新: 今」と表示され続けます。
- 区間ごとの「何分前の情報か」も分かりにくい（絶対時刻のみ）。安全情報では「◯分前」表示や、古い情報の透明度を下げるなどの鮮度表現が有効です。

### 2-9. 【中】ローディング・エラー表示
- 自動更新時はローディングが出ないため、25MB の取得中は無反応に見えます。
- エラー時は小さく「更新エラー」と出るだけで、再試行ボタンも理由もありません。
- データがゼロ件（キャッシュ未生成含む）の場合、何も表示されず案内もありません。

### 2-10. 【低】モーダルの操作性
- `Esc` キー・背景クリックで閉じられません。
- 期間の候補（直近3時間/昨日/先週の同時刻 など）のプリセットがあると便利です。
- ボタンラベル「📅 カレンダーで過去データを検索」は長く、絵文字は環境によって表示が変わります。

### 2-11. 【低】詳細パネルの情報の見せ方
- 「画像名」はファイル名をそのまま出しており、利用者には不要な情報です。
- 画像が 280px 幅で小さく、拡大表示（クリックでライトボックス）がありません。
- 「閉じる」ボタンが 10px と小さい。

## 3. ユーザビリティ・機能面

### 3-1. 【高】スマートフォン・タブレット非対応
- `viewport` メタタグがなく、パネル幅 280px 固定・上部バー 80px 固定のため、スマホでは地図がほぼ隠れます。
- 冬季の道路情報は**運転前に手元の端末で見る**需要が大きいため、レスポンシブ対応（パネルの折りたたみ・ボトムシート化）の優先度は高いと考えます。

### 3-2. 【中】場所・路線から探せない
- 住所/地名検索、現在地ボタン、路線での絞り込み、市町村へのジャンプなどがありません。北海道全域を手で拡大していく必要があります。

### 3-3. 【中】危険区間の一覧がない
- 「危険（WIPS≦7.5）」「凍結」の区間を一覧で示し、クリックでその場所へ移動する機能があると、監視・注意喚起用途で有用です。

### 3-4. 【中】区間の時系列が見られない
- 選択区間について「この24時間で WIPS がどう推移したか」「画像の移り変わり」を見る手段がありません。小さなグラフや画像のサムネイル列が有効です。

### 3-5. 【中】表示状態を共有・保存できない
- 表示位置・モード・期間が URL に反映されないため、「この場所のこの時間の状態」をリンクで共有できません。
- リロードするとフィルタ設定やモードがリセットされます（`localStorage` 等で保持可能）。

### 3-6. 【低】キーボード操作・スクリーンリーダー
- 主要操作が `onclick` 付きの `span`（モーダルの×）など、フォーカスできない要素に依存しています。
- 凡例のカラーボックスに代替テキストがなく、色情報が読み上げられません。

### 3-7. 【低】観測点そのものを表示できない
- 区間に集約された結果のみで、実際の観測点（どこで撮影されたか）や観測件数が分かりません。データの信頼性を判断する材料として、高ズーム時に点表示を出す案があります。

### 3-8. 【低】凡例・ヘルプ
- WIPS と路面状態の関係、データの出典（車載センサ/バス）、更新間隔、免責事項などを示す「この地図について」が欲しいところです。

## 4. パフォーマンス

### 4-1. 【高】毎回 約25MB の JSON を全クライアントへ配信
- データなし区間も含めた全 47,410 本のジオメトリを、5分ごとに全利用者へ送っています。gzip 等の圧縮も設定されていません。
- 対策案（組み合わせ可）:
  - **ジオメトリは静的ファイルとして1回だけ配信**（ブラウザキャッシュ）、5分ごとの更新は「区間ID→値」の小さな JSON のみ。
  - Apache の `mod_deflate` / 事前 gzip で圧縮（GeoJSON は 1/5〜1/10 程度になる見込み）。
  - 座標の桁数削減、ベクタータイル化（PMTiles/MVT）。

### 4-2. 【高】`/api/roads/recent` が毎回 25MB を JSON パースし直している
- `json.load` → `jsonify` でファイルを毎リクエスト解析・再シリアライズしています（`app.py:40-42`）。`send_file` でそのまま返せば CPU・メモリ消費が大きく減ります。

### 4-3. 【高】`get_at` にインデックスがない
- 期間検索が毎回フルスキャンです（現状431万件で約0.5秒）。本番でデータが増え続けると cron・過去検索ともに線形に遅くなります。
- `CREATE INDEX idx_pointed_get_at ON pointed_road_data(get_at);` の追加を推奨（DBのスキーマ管理側との調整が必要）。

### 4-4. 【中】過去検索に期間上限がない
- 1か月で約10秒、1年分を指定すると数百万点の空間結合となり、メモリと時間を大量に消費します。同時に数人が実行するとサーバーが止まる恐れがあります。
- 対策案: 期間上限（例: 7日）、結果のキャッシュ、非同期ジョブ化。

### 4-5. 【中】Leaflet の SVG 描画で 47,000 本の線
- 既定の SVG レンダラーでは DOM 要素が数万個になり、低スペック端末やスマホで重くなります。`preferCanvas: true` や、ズームに応じた間引きで改善できます。
- `setStyle` で全区間を再スタイルするため、スライダー操作のたびに全要素を書き換えています。

### 4-6. 【中】cron のたびに道路 GeoJSON（約270MB）を読み直している
- `generate_cache.py` は毎回5秒かけて全 GeoJSON をパースしています。前処理済みのフィルタ結果を GeoParquet / pickle 等で保存すると短縮できます。
- 同様に、空間結合で毎回 `to_crs(6679)` を道路全体にかけています。投影済みデータを保持すれば不要です。
- `sjoin_nearest` に `max_distance=50` を渡せば、探索自体を早期に打ち切れます。

## 5. データ品質・ロジック

### 5-1. 【高】異常値・外れ値の扱い
- WIPS の分布に `-Inf`（20件）、負値（-59 など）、14〜16 付近の別の山（約20万件）があります。センサ種別の違いか異常値かを確認し、除外・補正ルールを決める必要があります。
- 平均集計のため、1件の外れ値が区間の色を大きく変えます（中央値の利用も一案）。

### 5-2. 【中】最寄り道路への紐付けの誤り
- 対象道路（高速・国道・主要地方道）以外を走行した観測点も、50m以内に対象道路があればそこへ紐付けられます（交差点付近・並行道路・高架下など）。
- 紐付け時に進行方向（連続する観測点の向き）と道路の向きの一致を見る、マップマッチング手法を検討する余地があります。

### 5-3. 【中】区間の粒度がデータ元依存
- N13 のセグメントは交差点ごとに細かく分かれており、隣接区間で色がまだらになりやすいです。一定距離（例: 500m）ごとにまとめる、路線単位で平滑化するなどの工夫で見やすくなります。

### 5-4. 【低】未使用のテーブル・ライブラリ
- `mesh_1km` / `mesh_10km` テーブル、`pydeck` パッケージは現在のコードでは使われていません。将来使うのか整理が必要です（メッシュは広域表示時の集約に使える可能性あり）。

## 6. セキュリティ

### 6-1. 【中】`innerHTML` への未エスケープ挿入
- 詳細パネルで DB 由来の `road_surface`・`image_path` 等をそのまま `innerHTML` に入れています（`app_main.js:128-141`）。データ投入元が信頼できる前提でも、`textContent` や DOM 生成に切り替えるのが安全です。

### 6-2. 【中】Flask 開発サーバーを本番で使用・全インターフェースで待受
- `app.run(host="0.0.0.0")` のため、Apache を経由せず `:5100` に直接アクセス可能な場合があります（Apache 側の `Require method GET` 制限も回避される）。
- 本番は gunicorn 等の WSGI サーバー + `127.0.0.1` バインド + systemd 管理を推奨します。

### 6-3. 【低】過去検索 API による負荷（DoS）
- 認証・レート制限なしで重い処理（4-4）を誰でも起動できます。期間上限やレート制限を推奨します。

### 6-4. 【低】外部 CDN 依存
- Leaflet / noUiSlider を unpkg・cdnjs から読み込んでおり、SRI（`integrity` 属性）がありません。CDN障害時は地図が表示されません。ローカル配信か SRI 付与を推奨。

### 6-5. 【低】README にサーバー設定ファイル名の一部が記載
- README に Apache 設定ファイル名（一部伏字）が載っています。リポジトリの公開範囲によっては伏せることを検討してください。

## 7. 運用・保守

### 7-1. 【高】キャッシュ生成の失敗に気づけない
- cron が失敗しても `/api/roads/recent` は古い `output_24h.json` を返し続け、画面上も気づけません（2-8 と関連）。
- 対策案: キャッシュに生成時刻を埋め込み、一定時間以上古ければ画面に警告表示。ヘルスチェック用エンドポイント（`/healthz`）を用意。

### 7-2. 【中】URL プレフィックスがハードコード
- `PrefixMiddleware` で `/WinterRoad-Overview-LineStyle` を固定しているため、`http://127.0.0.1:5100/` へ直接アクセスすると HTML 内の CSS/JS パスが `/WinterRoad-Overview-LineStyle/static/...` になり 404 になります（テストクライアントで確認済み）。**ローカル開発時に画面が崩れます。**
- 対策案: 環境変数（例: `APP_PREFIX`）で切り替え可能にする、または Apache 側で `X-Forwarded-Prefix` を付けて ProxyFix の `x_prefix` を使う。

### 7-3. 【中】README と実態の差異（本対応で README を整備済み）
- 手順では `.venv` を作るが cron 例と実環境は `venv`、cron 例のパスに全角「＃」が含まれる、など。
- 画像ディレクトリ（`static/images`）の配置方法が「旧インターフェース参照」のみで、本リポジトリだけでは再現できません。

### 7-4. 【中】ログ管理
- `print` によるログのみで、レベル分け・ローテーションがありません。`cron.log` は5分ごとに追記され続けます（logrotate 設定を推奨）。
- 過去検索のたびにサーバーログへ集計結果が出力されます。

### 7-5. 【中】テスト・CI がない
- 集計ロジック（最新値の取得、外れ値除外、時間判定）は不具合が混入しやすいため、小さなテストデータでの単体テストが有効です。

### 7-6. 【低】大きなバイナリを Git 管理
- `geojson.tar.xz`（約26MB）をリポジトリに直接含めています。更新のたびに履歴が肥大化します。Git LFS か、取得スクリプト（国土数値情報からのダウンロード）に置き換える案があります。

### 7-7. 【低】起動時にグローバルで道路データを読み込む
- `app.py` の import 時に読み込むため、複数ワーカー起動時はワーカー数分メモリを消費し、起動にも時間がかかります。

### 7-8. 【低】フロントエンドの構成
- グローバル関数・グローバル変数・インライン `onclick` に依存しており、機能追加で衝突しやすい構成です。ES Modules 化、`app_main.js` 内の取得処理の重複（`fetchRecentData` と `fetchHistoryRoadData` のレイヤー生成コードがほぼ同一）の共通化を推奨。
- `#loadingOverlay` / `.modal-overlay` の CSS で `display` が二重指定されています（後勝ちで `none`）。
